# Accounts, progress sync, and private lesson videos

CCI Study remains usable without an account. Guest progress is stored in a separate local profile. A signed-in learner gets a local profile keyed to their Supabase user ID, and can explicitly merge the guest profile into that account from **Settings → Account & Sync**. Signing out returns to the guest profile; it does not erase either profile.

Progress is written locally first. When online, the app merges progress for the 12 canonical CCI study decks: card attempts, best quiz scores, daily completion counts, and streak dates. Custom deck content and progress remain local because syncing user-created deck content requires a separate sharing decision. The app uses authenticated Supabase RPCs. The database compares a version number before each write; if another device updated the account first, the app reads the new version, merges both sides against the last shared snapshot, and retries. Per-device counters make those retries idempotent, and guest-import receipts are stored in the same versioned cloud snapshot so repeating an import does not add the same attempts twice. Only the authenticated user can call the RPCs. The browser uses the Supabase publishable/anon key; no service-role key belongs in this app.

Lesson recordings remain in the private R2 bucket. The client catalog contains only R2 object keys. Pages Functions validate the Supabase access token, set an HttpOnly video-session cookie, and stream R2 objects with byte-range support. The bucket must stay private and must not receive a public domain. Signed-out guests can still study locally but cannot retrieve video bytes.

The lesson player also supports English captions and a searchable, time-linked transcript. `content/lesson-transcripts.json` explicitly maps unambiguous, metadata-equivalent, or user-confirmed source SRTs to catalog video IDs; the build converts only those files to WebVTT. A user-confirmed selection records its basis and exact source SHA-256, which the build validates before conversion. PREDESTINATION II uses the explicitly selected original-wording source; its provenance and the remaining unresolved candidates are recorded in `docs/lesson-transcripts-review.md`. The 17 metadata-only duplicate selections explicitly list their equivalent sources; the build verifies that all differences are confined to exporter metadata before the first cue, preserving spoken text and timing. These mappings were enabled explicitly; title matching or equal timestamps alone never authorizes a new mapping. The generated payload lives in ignored, server-only `functions/_generated/lesson-transcripts.cjs`, bundled by Pages Functions. It is excluded from `dist` and native app packages. The `/transcript/<filename>.vtt` middleware serves it directly after validating the same video-session cookie and disables caching. The build removes legacy generated `.vtt` assets from `dist/transcript`; no R2 transcript upload or credentials are needed. Run the build before starting Wrangler or deploying so the server module exists. Do not add a transcript mapping based on a title alone when multiple non-identical SRTs exist; confirm the correct source first. The repository review does not establish actual playback synchronization.

Caption generation and browser transcript parsing share presentation cleanup for generic `Speaker N:` prefixes at the start of cue lines. It preserves real names and spoken mentions, text content, cue order, and timing. Source SRTs and raw parsing remain unchanged so source fingerprints and duplicate-review decisions retain their original evidence. Search, accessible seek-button labels, and timestamp targets use the cleaned cue text. The versioned app-shell cache refreshes the parser and transcript catalog; private transcript responses remain network-only and uncached.

## One-time setup

1. Create a Supabase project and enable email/password sign-in and public self-registration. No CCI approval workflow is used. Disable email confirmation if newly registered learners must be able to watch immediately; if confirmation stays enabled, learners must confirm their email before signing in.
2. Apply `supabase/migrations/20261103000000_user_progress.sql` to the project. It creates an RLS-enabled progress table with no direct client table access and two authenticated RPCs.
3. In the Cloudflare Pages project `cci-discipleship-quiz`, keep the R2 bucket private and add an R2 binding named `LESSON_VIDEOS` pointing to `cci-lesson-videos`. `wrangler.toml` declares this binding for deploys and local Pages development.
4. Set Pages production and preview variables `SUPABASE_URL` and `SUPABASE_ANON_KEY` (or `SUPABASE_PUBLISHABLE_KEY`). For a `sb_publishable_...` key, store only the key value; do not include an `Authorization` header prefix. These values are read by the Pages Functions; the app receives only the public URL and publishable key from `/api/auth/config`. After deployment, confirm `GET /api/auth/config` returns HTTP 200 with `configured: true` before testing sign-up. A 503 response means the active deployment is missing or rejecting the required values.
5. Keep `ALLOWED_APP_ORIGINS` in `wrangler.toml` set to the exact origins of native app builds that call the Pages API from a different origin. Wrangler deploys replace dashboard-only plain-text variables, so the repository is the source of truth for this setting. This repository uses Capacitor 8’s default `https://localhost` on Android and `capacitor://localhost` on iOS. Include `http://localhost` only for older Android builds that use it. For current and legacy builds, use `https://localhost,capacitor://localhost,http://localhost` in both environments. Web app requests are same-origin. Do not use a wildcard: credentialed API requests require the exact allowed origin. After deploying the configuration, verify account-config GET and session OPTIONS responses return the requesting native origin in `Access-Control-Allow-Origin` and `Access-Control-Allow-Credentials: true`. Missing native origins cause Settings to show “Retry account connection” instead of the sign-in form.
6. Deploy the Pages project after setting the binding and variables. No video upload is required: the catalog already maps all 109 existing R2 objects to the canonical lesson deck IDs.

Do not put Supabase service-role keys, R2 credentials, upload tokens, passwords, or user access tokens in this repository, `.dev.vars` committed files, or chat. Supabase Auth access tokens are held by the Supabase client and copied only to a Secure, HttpOnly cookie through the session function. The video cookie expires after at most five minutes; the app refreshes it every four minutes and when the learner returns to the app. Sign-out clears it. The cookie and all video responses are marked no-store.

## Local development and checks

Use `npm run dev` to build the app and run it with Cloudflare Pages Functions at `http://127.0.0.1:8000`. Copy `.dev.vars.example` to `.dev.vars` and enter the Supabase project URL and publishable key locally; `.dev.vars` is ignored by Git. The local Supabase project settings are separate from the Cloudflare Pages production and preview settings. A plain static server can run the guest study experience but does not provide Pages Functions, authentication, cloud sync, or video streaming. Local R2 playback also needs a local or remote R2 binding.

Run `npm test` for the existing tests plus account partitioning, progress merge/CAS, private video authorization, byte ranges, and lesson-catalog checks. Live authentication and actual R2 playback still require the Cloudflare and Supabase dashboard configuration above.
